# Aurora Jewels — Database Design

## 1. Database Architecture

The database is designed for:

* Cloudflare D1
* SQLite
* Drizzle ORM
* Astro serverless API routes
* 50–100 launch products
* Pakistan-first commerce
* COD-only checkout
* Guest checkout
* Optional customer accounts
* Product variants
* Inventory management
* Wishlist
* Reviews
* Orders
* Discounts/coupons
* Website/content management
* Basic sales/order analytics

The schema uses normalized relational tables with `TEXT` identifiers generated by the application layer.

No PostgreSQL-specific features, stored procedures, extensions, triggers requiring external infrastructure, or database-specific services are required.

### Order statuses

The implementation uses a conventional minimal lifecycle:

* `pending`
* `confirmed`
* `processing`
* `shipped`

### Payment statuses

* `pending`
* `cod_due`
* `paid`
* `failed`
* `refunded`

For the launch COD flow, new orders normally start with:

`payment_method = cod`

and:

`payment_status = cod_due`

# 12. Constraints

Important constraints include:

* User email is unique.
* Category slug is unique.
* Collection slug is unique.
* Product slug is unique.
* Variant SKU is unique.
* Coupon code is unique.
* Order number is unique.
* Content-page slug is unique.
* Homepage section key is unique.
* Product prices cannot be negative.
* Inventory quantities cannot be negative.
* Reserved inventory cannot be negative.
* Reserved inventory cannot exceed quantity.
* Review ratings are between 1 and 5.
* Coupon percentage values are constrained to sensible values.
* Order quantities must be greater than zero.
* Order monetary values cannot be negative.
* COD is the only payment method.
* User role is restricted to `customer` or `admin`.
* Product status is restricted to approved values.
* Order status is restricted to approved values.
* Review status is restricted to approved values.

# 15. Audit Fields

The SRS explicitly excludes a dedicated audit-log system.

Therefore the database uses only lightweight record lifecycle fields:

* `created_at`
* `updated_at`

Where soft deletion is justified:

* `deleted_at`

No separate:

* audit_events
* admin_action_logs
* change_history
* revision_history

tables are introduced.

`updated_at` records the last modification timestamp but is **not** considered a full audit trail.

---

# 16. Soft Deletion

Soft deletion is justified for business/catalog/content entities where historical references may exist.

Soft deletion is used for:

* Users
* Customer profiles
* Customer addresses
* Categories
* Collections
* Products
* Product variants
* Reviews
* Coupons
* Content pages
* Homepage sections

Soft deletion is **not** used for:

* Orders
* Order items
* Order addresses
* Inventory
* Relationship/junction records

Orders are retained as historical commercial records.

Products and variants referenced by historical orders should be archived/deactivated rather than physically deleted.

# 17. Normalization Strategy

The schema targets approximately Third Normal Form (3NF).

### First Normal Form

Repeated values are separated into related tables.

Examples:

* Product images → `product_images`
* Product variants → `product_variants`
* Order items → `order_items`

### Second Normal Form

Many-to-many relationships use junction tables.

Examples:

* `product_categories`
* `product_collections`
* `wishlist_items`
* `coupon_products`
* `coupon_collections`

### Third Normal Form

Independent entities are separated so attributes depend on their appropriate primary key.

Examples:

* Customer profile information → `customer_profiles`
* Saved addresses → `customer_addresses`
* Inventory → `inventory`
* Website content → `content_pages`

### Intentional Denormalization

Orders intentionally snapshot:

* Product name
* Variant name
* SKU
* Unit price

This is required to preserve historical order accuracy when catalog data changes.

Order totals are also stored because they represent the commercial result at checkout.

---

# 18. Currency Strategy

The database does not hard-code a monetary database type because SQLite/D1 does not provide a dedicated currency type.

All monetary amounts use integer minor units.

Example:

`2500 PKR` → `250000`

The application must consistently apply the chosen currency precision.

The launch seed uses `PKR`.

International currencies are not introduced because international commerce is excluded from launch.

---

# 19. Guest Checkout Strategy

Guest orders use:

`orders.user_id = NULL`

The order itself retains the required customer and delivery information.

This means:

* Account creation is not required.
* Guest orders remain complete.
* Registered customers can have linked order history.
* Order history does not depend on a customer's saved address remaining unchanged.

Guest wishlist persistence is not implemented because the SRS leaves that behavior open and confirmed wishlist functionality is for registered customers.

---

# 20. COD Strategy

The locked architecture requires COD-only checkout.

Therefore:

* `orders.payment_method` only accepts `cod`.
* No card table is created.
* No gateway transaction table is created.
* No payment token table is created.
* No online-payment credentials are stored.
* No payment-provider integration data is stored.

Payment-related order state remains in `orders.payment_status`.

---

# 21. Search Strategy

The launch architecture specifies SQL `LIKE`/full-text search for the small catalog.

The normalized schema therefore keeps searchable product information directly on `products`.

A future FTS5 virtual table can be introduced through a migration if search requirements require it.

No external search service is required.

# 23. Migration Strategy

Migrations should be maintained as ordered SQL migrations compatible with Cloudflare D1.

Example:

```text
migrations/
├── 0001_initial_schema.sql
├── 0002_indexes_and_constraints.sql
├── 0003_seed_content.sql
└── ...
```

### Migration rules

1. Every schema change receives a new migration.
2. Existing migrations are never edited after deployment.
3. Destructive changes require an explicit migration.
4. Historical order data must be preserved.
5. Product removal should normally use soft deletion or archival.
6. Foreign keys must remain valid.
7. Migrations must be tested against a local D1 database before production.
8. Drizzle schema definitions must remain synchronized with SQL migrations.
9. Production migrations must be applied through the project's D1 migration workflow.
10. Seed data must be separated from destructive production migrations.

### Initial migration order

1. `users`
